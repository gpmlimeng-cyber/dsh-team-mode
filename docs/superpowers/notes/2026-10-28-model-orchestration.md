# 模型与推理等级编排

> 目标：在质量不降的前提下把成本降到最低。成本两大部分：**上下文重复**（见 AGENTS.md 的成本纪律）与**推理等级错配**（本文件）。

## 1. 分档原则

按"这项工作失败一次要重做多少"决定档位，而不是按"它重要不重要"。

| 档 | 用于 | 典型任务 | 判错代价 |
|---|---|---|---|
| **high** | 需要读源码核证、下结论、判定对错 | 调研/审计、设计 spec、评审、并发与生命周期、数据迁移 | 结论错 → 整条线返工 |
| **medium** | 有明确规格、需要想一下但不需要发明 | 一般功能实现、契约/传输接线、修 bug（有复现） | 局部返工 |
| **low** | 规格已经把答案写死，只有机械动作 | 跟随实测值改常量、改文案、加图标、补测试断言、删除死代码 | 一次重跑 |

## 2. 角色映射（AgentTeams 成员）

```
researcher       high    读源码、给证据、下结论
domain-engineer  high    改 schema/服务（判错要修数据）
runtime-engineer medium  按已定接口接线（有测试兜底）
ui-engineer      medium  UI 实现（有截图与契约兜底）
reviewer         high    判对错，降档等于没评审
```

**例外**：同一个 ui-engineer 手上如果是机械活（改名/加图标/调常量），把该任务单独派给一个 `low` 档成员，而不是让 medium 成员顺手做——机械活塞进高阶模型是最大的浪费来源。

## 3. 任务侧写法

派任务时把"这活属于哪一档"写进 description 第一行，例如：

```
档位：low（机械）。按 t1 文档里的实测值把 5 个常量改掉，不要重新推导。
```

理由：模型会按任务语气分配自己注意力；写清"不要重新推导"能省掉大量无效探索。

## 4. 上下文侧的省法（与模型选择同等重要）

- **给证据，不给背景**：派任务时贴 `文件:行号` 与目标值，而不是让它自己去找；
- **一个任务一个目标**：混目标会让模型反复重读同一批文件；
- **收工时一次性汇总**，不要让每个成员都复述一遍全流程。

## 5. 什么时候必须升档

以下情况**不允许降档**，哪怕任务看起来很小：

1. 涉及 schema / 迁移 / 权限 / 计费；
2. 涉及并发、生命周期、会话回收（错一次会留孤儿会话）；
3. 需要判断"实现是否符合参考实现"（评审）；
4. 需求本身有歧义，需要先做判断再动手。
