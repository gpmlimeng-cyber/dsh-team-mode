# 待确认的寿命与复用

> 2026-10-28 · 借鉴 baize-bot 的"确认模型"，但**只取一半**：过期要能被看见和清掉，同一问题不要反复问。
> 不做：自动拒绝、授权三档（理由见 §5）。

## 1. 现状与两个真实痛点

我们的 escalation（待确认）现在：

- 有 `kinds: approval / question / blocked_task`、`status: open / lifted`、`mutedAt`（每小时限额）；
- **没有寿命**：一旦 `open` 就永久挂在列表里；
- **没有记忆**：同一类问题，重跑五次就问五次。

## 2. A. 过期标记 + 批量清理（不做自动拒绝）

```
超过 N 小时（默认 24）未处理的 open escalation：
  视觉：标灰 + 「已过期 3 天」+ 失去优先级排序
  动作：勾选 → 「清理选中」（批量 lifted，reason: expired）
```

规则：

1. **不自动拒绝**——自动拒绝把"我还没看"变成"团队自己放弃了"，等于替用户做决定；
2. 过期项**仍然可批准**（清掉或点开都行），只是不再占据视线；
3. 过期项**不进入**「今天」首页的"等你确认"，除非用户展开"更多"；
4. 批量清理要**二次确认**（这是不可逆的状态变更），并显示将清理的条数。

## 3. B. 同类问题记住答案（standing answer）

用户解决一条 escalation 时，可以勾选「以后同类自动这样」：

```
gate 签名 = `${kind}:${normalizedGateId}`
normalizedGateId：去掉数字、路径、时间等易变部分后的稳定前缀
```

- 存进团队聚合的新字段 `standingAnswers`（**不是**记忆条目，理由见 §4）；
- 上限 **20 条**，超出按最久未用淘汰；
- 运行时**在创建 escalation 之前**先查它：命中则以记录的答案直接放行，并**在消息流里留一行可追溯记录**（"按你 10-26 的答复自动通过"）；
- 用户在团队设置里能**逐条查看和删除**这些自动答复（否则就成了不可见的自动放行）。

## 4. 为什么不用团队记忆存它

记忆是**给人看的自然语言**，需要模型理解；standing answer 是**给程序做精确匹配的键值**。混在一起的结果是：模型可能改它、总结它、或让它变得不精确。**机器契约放机器字段。**

## 5. 明确不做

| 不做 | 理由 |
|---|---|
| 自动拒绝过期的确认 | 见 §2.1：那是替用户放弃 |
| 授权三档（单次/本项目/永久） | 我们的确认不是工具授权，是任务被卡住；档位解决不了"同一问题反复问"，记住答案才能 |
| 硬清单（花钱/账号/删文件永不永久） | 我们的成员跑在宿主已有的权限门之下，重复造会与该门冲突 |
| 交接接受制 | 成员是模型，会秒点接受，多一次握手零收益 |

## 6. 与「今天」首页的关系

首页「等你确认」区是这两个机制的唯一入口：

- 列表只显示**未过期**的等待项；过期项在「更多」里，带清理按钮；
- 每条等待项的快捷动作里带「以后同类自动这样」，勾上即创建 standing answer。

**不要在首页之外再开一个确认中心**——一处就够。

## 7. 验收

1. 超期项显示"已过期 N 天"且排序下沉，可批量清理（二次确认）；
2. 清理后状态 `lifted`，不删除记录（可追溯）；
3. 勾选"以后同类自动这样"后：**同签名**的 escalation 不再出现，且消息流里有一行自动放行的可追溯记录；
4. standing answer 上限 20，超出淘汰最久未用；
5. 团队设置里能查看/删除每条 standing answer；删除后同类问题恢复询问；
6. 不同签名的 escalation 不受影响（不能因为一条答复放行一大类）；
7. `npm run check` 全绿。
