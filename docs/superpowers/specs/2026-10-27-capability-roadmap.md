# 功能差距倒推与规划（从「新建助手」反推）

> 2026-10-27 · 目标插件 `@limeng/dsh-team-mode` · 状态：待评审
> 输入：`docs/research/assistant-create-parity-audit.md`（创建界面的字段差距）
> 方法：**界面缺什么 = 字段缺什么 = 产品能力缺什么**；每一项再分「DSH 已提供 / 需要我们造 / 不该做」

## 一、从创建界面反推出的 9 个能力缺口

| # | 创建界面缺的 | 反推出的能力缺口 | 谁该提供 |
|---|---|---|---|
| A | 标题/副标题 | 助手**身份层级**：name 之外没有 title（职能）与 blurb（一句话介绍） | 我们（缺字段） |
| B | 独立人设 + 回复风格 | **人格分层**：现在只有一个 `instructions`，人设与"怎么说话"混在一起 | 我们（缺字段） |
| C | Skills / MCP 不可选 | **能力装配**：模板能配 Skills/MCP，实例直建却写死 `[]`，用户以为模板没生效 | 我们（**能力缺口，非产品选择**） |
| D | 记忆无创建期草稿 | **记忆预置**：只能建完再编辑 | 我们（低优先） |
| E | 没有 Routines | **按助手的定时/例程** | **DSH 已有**「自动化任务」面板 |
| F | Access 只有工作区 | **运行环境**：浏览器/电脑/连接器/云后端 | DSH 有权限预设与沙箱；浏览器/电脑是 MausBot 特有 |
| G | 权限只有 preset | **权限细项**：审批模式、命令白名单、外发策略、peers | **DSH 有权限预设体系**；peers 是团队概念 |
| H | 没有通知/语音 | **通知与语音** | 通知 DSH 有；**语音我们没有通道** |
| I | 没有汇报对象 | **组织关系**：reportsTo | 我们有 Team（更强的组织单元），不需要逐级汇报 |

**关键判断**：E / F / G / H(通知) 四项**不该由我们重造**——DSH 已经提供了对应机制，正确做法是"接上宿主能力"，而不是在插件里再写一套调度/权限/通知。真正属于"我们造"的是 A / B / C / D / I(不做)。

## 二、逐项规划

### P1 · 能力装配（C）——唯一一条"用户会踩坑"的缺口

**现状**：模板（assistant template）可以配 `skillAllowlist` / `mcpServers`；但 `assistant.instance.create` 直接建实例时把这两个**写死为 `[]`**，而 `updateAssistantInstanceInputSchema` 也不开放它们。结果：用户从模板建助手，以为继承了模板的能力，实际没有。

**MausBot 的做法**（`bot-settings/SkillsSection.tsx` + bot 的 skills 字段）：技能是 bot 的一等字段，创建时可勾、之后可改。

**我们要做的**：
1. 让 `createAssistantInstanceInputSchema` 接受 `skillAllowlist` / `mcpServers`（**既有字段开口**，不新增 transport）；
2. `updateAssistantInstanceInputSchema` 同样开放（否则建完改不了，等于半条腿）；
3. 创建对话框「模型与环境」区加一段「能力」：模板带过来的默认勾选 + 可增删；
4. 服务层校验：技能必须存在于 catalog（和团队成员的技能校验同一条路）。

**验收**：从带 Skills 的模板创建 → 实例快照里技能非空；改技能后再建会话，会话工具集包含新技能。

**成本**：小（字段开口 + 一个多选区 + 校验复用）。

### P2 · 身份层级（A）——低成本、高辨识

**现状**：实例快照只有 `name / avatar / instructions`。侧栏一行、详情面板都只有一个名字。

**要不要做，取决于一个真问题**：用户会不会有多个"同名但职责不同"的助手？如果有（比如两个都叫「调研」），title 就有价值；如果没有，它只是一行没人填的文本。

**建议**：**暂不做**，等出现真实的多助手场景再评估。记入 PARKED。

### P3 · 人格分层（B）——产品方向问题，不在这轮

MausBot 把「soul（你是谁）」与「reply style（怎么说话）」分开。我们的对齐 spec 已明确不搬 soul。**保持现状**：一份 instructions 足够支撑当前使用；两层人格会在团队协作里制造"这个成员到底按哪份人设说话"的歧义。

### P4 · 记忆预置（D）

**现状**：记忆只能在设置里编辑（`assistant.memory.*`），创建时不能预置。

**判断**：低价值。记忆是**用出来的**，不是建出来的；创建时塞草稿反而让用户在不知道用途时面对一个空文本框。**不做**。

### P5 · 例程（E）——接 DSH 的自动化任务，不自造

DSH 有「自动化任务」面板（我们 BOT 模式把它放在底部控制栏）。正确做法：
- 助手详情面板里加一段「自动化」，**列出属于该助手的自动化任务**并给一个跳转；
- 不在插件里实现 cron/调度（那是宿主能力）。

**验收**：详情面板能看到该助手的自动化任务数量与入口；没有时显示空态说明去哪儿建。

### P6 · 权限细项（G）——先确认 DSH 权限预设够不够

我们现在只有 `permissionPresetId`（读/写/全权档位）。MausBot 的细项（命令白名单、外发策略）在 DSH 里可能已经在预设内部实现。

**行动计划**：先做一次**只读核对**——读宿主权限预设的定义，确认它是否已含命令级限制；若已含，**不做**；若不含，再评估。

### P7 · 语音/通知（H）——只做通知，不做语音

DSH 有通知机制；语音我们没有通道。**只考虑**把"助手产生了需要你知道的事"接到宿主通知上，不造 TTS/STT。

## 三、执行顺序与理由

```
P1 能力装配        ← 唯一会误导用户的缺口，先修
P6 权限核对（只读）  ← 决定是否需要后续工作，成本仅一次调查
P5 例程接宿主      ← 面板里加一段 + 跳转，小
P2/P3/P4/P7        ← 记录为不做或搁置，写进 PARKED
```

**为什么 P1 第一**：其余差距用户大多感知不到（title 不填也没事、记忆不用预置），只有 P1 是"我明明配了模板，建出来却不带能力"——这是**承诺与实现的落差**，不是缺功能。

**为什么 P6 先核对**：避免为"DSH 已经做了的事"再造一遍。上一轮我们已经因为"没查清楚就下结论"吃过亏（我说过仓库没有成员级清空接口，实际有）。

## 四、对齐 MausBot 代码的方式

每一项实现前先读它对应的 `bot-settings/*.tsx` 与 `state/store.tsx` 里的字段，做三件事：

1. **抄字段语义**（它这个字段解决什么问题），不抄 UI 形状；
2. **抄交互约束**（例如技能必须存在于 catalog、权限变更只影响之后的会话）；
3. **明确不抄的部分**并写进 commit message（例如 soul、peers、reportsTo），避免"看起来对齐了、其实是空壳"。
