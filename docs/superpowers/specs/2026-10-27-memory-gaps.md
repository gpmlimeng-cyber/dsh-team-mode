# 记忆四项补齐（下一批）

> 2026-10-27 · 状态：待排期（等 `avatar-editor` 团队收尾后开新团队）
> 背景：对比 MausBot / DeepSeek-Bot 的记忆实现后的四项缺口，按价值排序。

## 结论先行

**不向文件方案靠拢**（MausBot 的 Markdown 文件夹），理由是它做不到我们已有的三件事：`visibility: private/team-safe`、`status: proposed/superseded/archived`、`revision + undo`。
**吸收 DS Bot 的两个交互**（条数行、一句话问/改），**补上群聊记忆**，**加一个有约束的自动捕获**。

## M1 记忆条数行 + 管理入口（最小、先做）

- 位置：助手详情面板的「记忆」区块顶部，一行：`记忆 · 12 条 · 管理 →`
- 数据：`assistant.memory.get` 已在读，直接取 `entries.length`；
- 空态：`记忆 · 还没有记录`，点进去就是新建；
- 点击：打开设置面板并展开「记忆」分组（复用概览的跳转机制）。

**验收**：条数随写入实时变；空态不显示 0；从详情面板能一步到记忆编辑。

## M2 群聊级记忆（DS Bot 有，我们缺入口）

现状：`teamAggregateSchema.memory`（`teamMemorySchema`）**已有数据**，但没有像样的 UI 入口，用户无从知道"这个群记得什么"。

- 归属：团队（不是成员），与助手的记忆互不干扰；
- 写入者：**Leader 会话的工具**（可直接写 active）+ 成员的 `team_memory_propose`（只写 proposed，Leader 用 `team_memory_accept` 采纳或拒绝）+ 设置里的显式编辑；
- 读取：注入 Leader 的系统提示（群聊上下文），成员会话**不注入**（避免"谁的记忆"混淆）；
- UI：团队页新增「记忆」区块，列表 + 编辑，复用助手记忆的条目组件（同一套 `MemoryEntry`，`scope: team`）；
- 可见性：群记忆天然 `team-safe`，**不提供 private**（不然成员看不到就失去意义）。

**验收**：群记忆与助手记忆互不串；成员会话不注入群记忆，也不能直接写 active（只能 propose，由 Leader 决定）；Leader 的提示注入 active 条目。

## M3 「问 / 改」一句话操作（DS Bot 的 Ask or update）

一次模型调用完成两件事之一：

- **问**：基于现有条目回答问题（不改数据）；
- **改**：提出增删改，**走既有写入路径**（`assistant.memory.entry.write`，带 revision 校验），不绕过状态机。

约束（写进契约，防止变成"模型随便改记忆"）：

1. 新条目一律以 **`status: proposed`** 写入，除非用户在 UI 里点了「采纳」；
2. 调用必须**显式触发**（用户点按钮 / 发一句），不做后台轮询；
3. 失败要显示原因，**不静默丢弃提议**；
4. 返回结构固定：`{ kind: 'answer' | 'change', answer?, entries? }`，前端据此渲染。

**验收**：问不产生写入；改产生的条目是 `proposed`；revision 冲突时提示并保留草稿。

## M4 自动捕获开关（MausBot 有，我们缺；但必须有约束）

- 开关位置：助手设置「记忆」分组顶部，`自动记录`（默认**关**）；
- 触发：一轮对话结束后，由模型提议 0–3 条候选记忆，**全部写为 `proposed`**；
- 去重：与现有条目做文本相似度去重（简单前缀/包含判定即可，不引入向量）；
- 上限：每次最多 3 条、每轮最多一次；用户在 UI 里批量「全部忽略」；
- **成本**：开关打开后每轮多一次模型调用——必须在 UI 上写明这一点，不能偷偷花钱。
- 刷新：自动捕获与问/改的写入没有面板动作，所以记忆区块和概览条数在窗口重新可见（`focus` / `visibilitychange`）时重读一次；没有轮询，也没有服务端推送，这是当前已知的限制。

**验收**：默认关闭；开启后只产生 `proposed`；忽略后不再重复提议同一条；关闭后立即停止。

## 排期（下一批）

```
T1  M1 条数行（小，先合，可单独上线）
T2  M2 群聊记忆（数据已有，主要是 UI + 注入范围）
T3  M3 问/改（服务端一次调用 + 前端渲染）
T4  M4 自动捕获（依赖 M3 的写入路径）
T5  评审（M2/M3/M4 各自独立契约，M1 并入 T2 的评审）
```

依赖关系：M3 依赖 M1 的读路径；M4 依赖 M3；M2 独立，可与 M1 并行（不同文件）。

## 附录：什么时候自动记，什么时候问人（2026-10-28 补充）

原文写的是"M3/M4 一律写 `proposed`"，**太粗**——那会让用户每天面对一堆确认卡。改为按「错的代价 × 可逆性」分三档：

| 情形 | 处理 | 理由 |
|---|---|---|
| 用户**明说**"记住 X" | **直接写 `active`** | 已授权，再问一遍是侮辱 |
| 任务**结论性事实**（"这仓库用 pnpm"） | **自动写 `active`**，标来源、可撤销 | 错记代价低，一句话能纠正 |
| 模型**推断的偏好** | 写 `proposed`，**需确认** | 推断常错，而偏好会长期影响所有输出 |
| **跨成员可见**（`team-safe`） | **必须确认** | 影响别人；被别人引用后撤销不回来 |
| **敏感信息**（账号、客户、他人评价） | **必须确认** | 不可逆的暴露面 |
| 与现有条目**语义重复** | **静默丢弃**，不确认 | 确认"我已经知道的事"是纯噪声 |

原则：**确认是事前摩擦，撤销是事后成本**。默认自动写 + 显眼撤销，只在"错的代价高 / 不可逆 / 影响别人"时才事前拦一道。

两条配套硬约束：

1. **撤销必须比确认更容易**：每条记忆一个"删掉"；删掉后在聊天流留一行"已忘掉 X"，让用户看见它真的没了；
2. **`proposed` 不能永久挂着**：超过 24 小时未确认**自动归档**（不是拒绝），列表里显示"已归档 3 条"，避免设置页堆一片没人理的待办。

确认卡的形态：**就在发生的那条会话里**（聊天内卡片），按钮只有「记住 / 不用记」——**不给"编辑后再存"**，那是在要求用户替你写记忆。设置页的记忆列表只作归档视图。
