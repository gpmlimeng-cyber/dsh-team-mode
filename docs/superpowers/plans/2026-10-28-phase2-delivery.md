# 阶段二：交付可见、可验、可救

> 2026-10-28 · 前置：阶段一对齐完成（10 项核心任务 ≥ 9 项）。
> 目标：把“团队能力”变成用户能看见、能相信、能恢复的交付。

## 原则

```text
不新增第二套聊天
不重写团队引擎
先做“看见”，再做“更强”
每个功能必须能回答：用户下一步做什么
```

## 顺序

### 1. Team Run 总览

一次团队运行的单一页面：

```text
目标
团队（Leader / 成员 / 线程）
任务板（待办 / 进行 / 待评审 / 完成 / 失败）
产物
评审结果
失败与重试
token / 时长
```

验收：

```text
用户不用展开每个 Session 就能知道这次交付到哪一步
任一任务可点进原生 Session
```

### 2. 交付证据

每个任务可展开：

```text
负责人 / attempt
改动文件 / 提交
测试命令与结果
产物链接
评审人 / verdict / findings
```

验收：

```text
每条完成声明都有证据
没有证据的任务不能显示“已完成”
```

### 3. 评审门禁可视化

```text
待评审
通过
需要修改（列出 findings）
被拒绝
```

验收：

```text
用户能看到“谁验的、验了什么、为什么没过”
失败评审可一键生成修复任务
```

### 4. 失败恢复

单一入口：

```text
重试任务
换成员接管
回滚到上一个 checkpoint
重建线程（保留记忆与任务）
```

验收：

```text
任何失败都能从任务行进入恢复
恢复不丢团队、任务、记忆
```

### 5. 每次 Run 成本

```text
总 tokens
按成员 / 任务
时长
失败重试次数
```

不做：

```text
币种 / 账单
历史趋势
provider/model 拆分
```

验收：

```text
一次 Run 结束能看到成本
超预算有提示（不做自动停止）
```

### 6. 并行 Run

```text
同一团队多线程并行
多仓库 / 多目标
队列与依赖
```

验收：

```text
并行不串任务
每个 Run 有独立总览
```

### 7. 多人协作

```text
共享一个 Run
评论 / 接管 / 审批
```

这一项依赖宿主能力；先不做，等前六项稳定。

## 指标

```text
首次交付时间
任务评审通过率
失败恢复成功率
每次交付 token / 时长
7 天内再次发起 Run 的团队比例
```

## 决策门

```text
Run 总览上线后：
  如果用户仍然只开一次 → 停止加功能，访谈
  如果第二次率上升 → 继续证据/恢复/并行
```

## 不做

```text
第二套聊天
自建浏览器/电脑/语音
费用账单
组织架构
模板市场
```

## 队列

```text
阶段一收尾
  模板 → 公告 → batch polish → 首次引导 →
  通知/归档 → 身份 → 搜索 → 归档恢复 → 对齐审计

阶段二
  Run 总览 → 交付证据 → 评审门禁 →
  失败恢复 → Run 成本 → 并行 → 多人协作
```
