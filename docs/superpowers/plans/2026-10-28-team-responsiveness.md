# 团队响应速度专项

> 2026-10-28 · 目标：团队模式的“聊天体感”接近单聊，而不是每句话都像启动一个项目。
> 不改原生聊天/输入框，不做假进度，不引入第二套编排器。

## 1. 问题定义

单聊没有结构差距；团队差距在**首响路径**：

```text
用户发消息
→ Leader 读上下文 / 调工具
→ 判断模式
→ 可能先要用户确认
→ 创建任务 / 拉成员
→ 成员启动
→ 成员执行
→ Leader 汇总
→ 才出现完整回答
```

用户感知到的不是“模型慢”，而是：

```text
先安静很久
然后突然开始动
简单问题也被当成项目
```

## 2. 当前已存在的机制（不是从零加）

`src/runtime/team-prompts.ts` 已有三模式：

```text
对话/direct      → 直接回答
单任务/single    → 一个任务、一个 owner
编排/orchestrated → 多任务、多成员、评审
```

但有两个结构性拖慢点：

1. **首轮强制确认**
   `LEADER_RULES` 要求首轮先 `team_members` → 提 roster/plan → 等用户批准，之后才 spawn/assign。
   对“已经建好、成员已存在”的团队，这一步是重复确认。

2. **先建流程，后出字**
   Leader 先调工具、建 Goal/Task，再给用户可见回复；没有“已收到、正在做”的即时反馈。

## 3. 目标与指标

### 体验目标

```text
简单问题：团队直接答，不做任务编排
首次反馈：用户发出后 2 秒内有可见状态
普通任务：首响不晚于单聊的 1.5 倍
多成员任务：并行启动，不串行等待
```

### 指标

```text
TTFB（首 token）
首条可见状态时间
direct 模式占比（简单问题应高）
delegation rate（不该分派的比例）
任务启动到首个成员开跑的时间
端到端完成时间
每次回答 token 成本
```

### 基线

先测，不猜：

```text
12 条固定提示
  4 条纯问答
  4 条单文件/单任务
  4 条多成员任务
记录 leader / member / 汇总各段耗时
```

## 4. 杠杆（按收益/风险排序）

### L1 · 已建团队不等 roster 批准

```text
团队已有成员、用户直接给任务
→ Leader 立即执行
→ 只有“新建团队 / 加成员 / 改变范围”才请求批准
```

预期：去掉最大的一段空白等待。
风险：Leader 在范围不清时擅自开工。
约束：保留“范围/风险需要用户决策时才问”。

### L2 · 先确认收到，再开始做事

```text
需要超过几秒的工作
→ Leader 先给一条短确认（不假装完成）
→ 再调工具
```

实现优先级：

```text
先做运行时状态行（不改模型行为）
  收到 / 正在分派 / 成员处理中
再考虑 Leader 文案确认
```

风险：假进度会伤害信任。
规则：只显示真实状态，不显示未发生的步骤。

### L3 · 并行启动，不串行等第一个成员

```text
创建全部任务
→ 一次性并行唤醒需要的成员
→ 不 await 第一个成员完成再叫第二个
```

现状：任务创建/成员唤醒在 Leader 回合内串行。
风险：并发成本、文件冲突。
约束：只并行无依赖任务；有 `blocked_by` 的仍串行。

### L4 · 减少每轮上下文

```text
只注入当前需要的记忆/公告/分区指令
不要每轮把所有段落都塞进 prompt
```

现状段落：

```text
assistant memory 9
identity/roster 10-11
group brief 8
team announcement
```

风险：删太多会丢约束。
做法：先测量各段 token 占比，再按“当前模式”裁剪，不全局删除。

### L5 · Leader 轻量路由

```text
简单问答用更快的模型/更短上下文
复杂任务再用完整 Leader 提示
```

风险：路由错误、两套行为。
先做提示层，不引入第二个编排器。

## 5. 分阶段

### P0 · 测量（不改行为）

```text
给现有链路加时间戳：
  user message
  leader first token
  first tool call
  first member start
  first member token
  leader summary start/end
跑 12 条基准，产出基线表
```

验收：能回答“慢在哪一段”。

### P1 · 快速通道

```text
已建团队直接开工
direct 模式直接答
只有范围/风险问题才请求批准
```

验收：

```text
纯问答不产生 Goal/Task
简单任务不出现 roster 确认
TTFB 相对基线下降
```

### P2 · 即时状态

```text
团队聊天里出现真实状态行：
  已收到
  正在分派
  成员处理中
  等待复核
不伪造完成
```

验收：2 秒内有可见反馈；状态与真实事件一致。

### P3 · 并行分派

```text
无依赖任务并行唤醒
有 blocked_by 串行
```

验收：多成员任务启动时间不再线性叠加。

### P4 · 上下文与路由

```text
按模式裁剪 prompt
测量 token 占比
再决定是否做模型路由
```

验收：同等质量下 token/首响下降。

## 6. 验收与回滚

```text
每个阶段单独提交、单独开关（如需要）
质量基准：12 条提示的答案质量不能下降
失败回滚：保留上一版 prompt/流程，不破坏已有团队
```

## 7. 不做

```text
假 typing / 假进度
自绘聊天界面
第二套 Agent 编排器
为了快而跳过评审门禁
把复杂任务强行 direct
```

## 8. 任务拆分

```text
T1 基线测量与埋点
T2 P1 快速通道（prompt + 首轮规则）
T3 P2 真实状态行
T4 P3 并行分派
T5 P4 上下文裁剪
T6 独立验收 + 基准对比
```

## 9. 一句话

```text
不是让模型更快，
是让团队在正确的时候不做多余的事。
```
