# 产品洞察与落地建议

> 2026-10-23 · 团队模式 / 多 Agent 产品方向
> 用途：约束后续功能取舍，避免为了“更多 Agent”而偏离产品价值

## 一句话定位

> **DSH 原生的、可审计的团队执行层。**  
> 不卖“更多 Agent”，卖“交接、审批、恢复、可追责”。

## 核心洞察

### 1. 瓶颈是上下文所有权，不是任务拆解

任务图回答“谁做什么”，上下文图回答“谁知道什么”。

团队失败通常不是任务没拆开，而是：

- 成员拿到过期上下文
- 主 Agent 不知道成员改了什么
- 交接只传结论，丢了约束
- 压缩后关键细节消失

优先级：checkpoint、handoff、context ownership，高于继续加 Agent。

### 2. 团队的主要价值是独立验证，不是并行

多个 Agent 并行经常在重复劳动。稳定产生价值的是：

```text
一个执行者
+ 一个不能自己验自己的验证者
+ 一个有权说不的审批者
```

2–3 人的对抗结构，通常比 6 个人的协作结构更可靠。

### 3. 审批是留存界面，不是权限弹窗

用户留下不是因为 Agent 聪明，而是因为“知道什么时候该自己拍板”。

失败模式：

- 弹太多 → 无脑同意
- 藏太深 → 干脆不用
- 没历史 → 不知道上次怎么决定

核心指标：**每个完成任务打断用户几次。**

### 4. 聊天是界面，账本是真相

不要把系统状态存在消息里。消息是投影，真相应是：

```text
Task / Attempt / Goal
Checkpoint / Handoff
Approval decision
Team Epoch
```

聊天负责意图和信任；账本负责恢复、审计、追责。

### 5. 团队需要运维层，不是更多角色

Agent 团队会自然产生组织熵：

- 僵尸 worker
- 过期任务
- 重复记忆
- 失效 attempt
- 换 Leader 后的孤儿会话

每日 tidy / GC / 预算 / 归档，比再加一个 Research Agent 更有价值。

### 6. 最缺的是评估，不是功能

需要回答：这个团队真的比一个 Agent 更好吗？

团队评分卡：

- 任务成功率
- 人工打断次数
- 从提问到决策耗时
- 返工率
- token / 成本
- 上下文丢失次数
- 审批拒绝率

没有评分卡，多 Agent 很容易变成“看起来很忙”。

### 7. 模型更强后，团队更像剧组，不像公司

- 成员更少，角色更硬
- 默认单 Agent + 工具
- 团队只在长周期、高风险、多方向、多责任方时成立

角色会从“多面手员工”变成责任边界：Owner、Verifier、Approver、Researcher。

## 产品落地建议

### 先做什么

1. **过可靠性门**
   - 测试稳定
   - 真实宿主重启
   - 恢复 / 审批 / 归档真实路径
   - 发布前固定 gate

2. **主 Agent 作为唯一 P1**
   - 同一 profile 双模式：原生 / 团队
   - 团队默认进 Leader 主会话
   - 团队面板：成员 / 任务 / 审批 / 依赖
   - Leader prompt：直接回答 + 收口
   - 并行视图改为显式进入

3. **团队默认 2–3 人**
   - 默认模板：1 执行 + 1 验证
   - 复杂任务 +1 研究/审批
   - 上限 5 人
   - 超过 5 人提示拆 Goal

4. **审批和注意力当核心功能**
   - 批量、按风险排序
   - 低风险不打断
   - 高风险必须人拍板
   - 保留历史决策

5. **先做运维层**
   - 僵尸 worker 清理
   - 过期任务归档
   - attempt / epoch 恢复
   - 每日 tidy
   - 预算 / 超时

### 先不做什么

- 全局 Captain
- 自建云电脑 / 浏览器 / 连接器
- 多 Host
- 外部 npm 发布前的大功能扩张
- 为对标 Grok Bot 复制消费级壳

## 建议顺序

```text
第 1 周  可靠性门 + 主 Agent MVP
第 2 周  团队面板 + 提示词 + 截图回归
第 3 周  协作总览 + 评分卡
第 4 周  审批/注意力优化 + 真实重启 + 可演示版本
```

## 决策原则

> 如果一个功能不能改善 **可归因、可交接、可审计、可运营** 中的至少一项，就不做。
